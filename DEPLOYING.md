# Deploying Mu Katale

Two hosts, because the app splits cleanly in two: a static bundle and a server
that talks to Postgres.

| Piece | Where | Published by |
| --- | --- | --- |
| Shop (Vite SPA) | GitHub Pages | `.github/workflows/deploy-pages.yml` |
| API (Next.js routes) | Render web service | `render.yaml` |
| Database | Render Postgres | `render.yaml` |

The Pages site is served from one origin and the API from another, so a session
cookie is a third-party cookie. That is the whole complication in this document,
and it is handled by one variable on the API: `WEB_ORIGINS`
(see `api/src/lib/webOrigins.ts` for what turning it on changes).

## Before you start

Two values have to know about each other. Both are origins only — scheme and
host, no path, no trailing slash.

| Value | Where it lives | Example |
| --- | --- | --- |
| `API_BASE_URL` | GitHub → Settings → Secrets and variables → Actions → **Variables** | `https://mu-katale-api.onrender.com` |
| `WEB_ORIGINS` | `render.yaml`, and the Render dashboard for the service | `https://rwangoga.github.io` |

Vite inlines `API_BASE_URL` at build time, so changing it means rebuilding the
frontend, not just redeploying. `WEB_ORIGINS` is read at request time.

## 1. API on Render

1. Push this branch to GitHub.
2. Render dashboard → **New+** → **Blueprint** → select the repo. Render reads
   `render.yaml` and offers to create `mu-katale-api` plus `mu-katale-db`.
3. Wait for the first deploy, then open `https://<service>.onrender.com/api/health`.
   `{"status":"ok"}` means the service and the database are both reachable;
   a `503` means it cannot connect to Postgres.
4. Note the service's URL — it is `API_BASE_URL` in the table above. The
   generated name comes from `name` in `render.yaml`, so rename it there if you
   want a tidier one before the first deploy.

`PAYMENT_WEBHOOK_SECRET` is generated by Render and never committed. Nothing
posts to the webhook route yet, so its only job is to make a missing secret a
boot failure rather than a silent default.

## 2. Load the database once

Render's free plan has no shell access and no one-off jobs, and a pre-deploy
command is a paid feature, so schema and seed data are applied from your machine
against the hosted database. Copy the **External connection string** from the
Render database page (the internal one is only reachable inside Render).

```bash
cd api
DB='postgresql://user:password@dpg-xxxx-a.frankfurt.render.com:5432/dbname'

ADMIN_EMAIL=you@example.com ADMIN_PASSWORD='at-least-10-characters' \
ADMIN_NAME='Your Name' DATABASE_URL="$DB" npm run db:push && \
ADMIN_EMAIL=you@example.com ADMIN_PASSWORD='at-least-10-characters' \
ADMIN_NAME='Your Name' DATABASE_URL="$DB" npm run db:seed
```

`db:push` creates the tables, `db:seed` loads the catalogue, the geography, the
opening stock ledger, the promos and the staff account — the admin step is part
of that chain and needs the three `ADMIN_*` variables. Every seed script is
idempotent, so re-running it is safe. It reads `DATABASE_URL` from the
environment, not from `api/.env.local`, which is why it is passed inline.

Demo orders come from `npm run db:backfill:orders` with the same inline
`DATABASE_URL`, when you want the staff area to have something to process.

## 3. Shop on GitHub Pages

1. GitHub → Settings → **Pages** → Build and deployment → Source: **GitHub
   Actions**. Leaving it on "Deploy from a branch" makes the deploy job fail.
2. Add the `API_BASE_URL` variable from the table above.
3. Push to `main`, or run **Deploy shop to GitHub Pages** manually from the
   Actions tab. The site appears at the URL the workflow prints, and the job
   fails before publishing if the bundle does not match that URL.

The workflow passes the Pages base path (`/<repository>/`) to Vite as
`VITE_BASE`, and `App.tsx` reads it back out of `import.meta.env.BASE_URL` for
the router's basename. It also copies `index.html` to `404.html`, which is how a
deep link such as `/checkout` survives a refresh on Pages.

## 4. Prove the cross-origin contract

Run these against the deployed API. Replace both URLs with your own.

```bash
API=https://mu-katale-api.onrender.com
PAGES=https://rwangoga.github.io

# 1. A GET from the shop must come back with the shop's origin and credentials.
curl -s -D - -o /dev/null "$API/api/products" -H "Origin: $PAGES" \
  | grep -i "access-control"
# expect: access-control-allow-origin: https://rwangoga.github.io
#         access-control-allow-credentials: true

# 2. The preflight must be answered before any route sees it.
curl -s -D - -o /dev/null -X OPTIONS "$API/api/cart" \
  -H "Origin: $PAGES" -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: content-type"

# 3. A stranger must get no CORS headers at all.
curl -s -D - -o /dev/null "$API/api/products" -H "Origin: https://evil.example" \
  | grep -i "access-control"   # expect nothing

# 4. Signing in must set a cookie a cross-site browser is allowed to store.
curl -s -D - -o /dev/null -X POST "$API/api/admin/login" \
  -H "Origin: $PAGES" -H "content-type: application/json" \
  -d '{"email":"<staff address>","password":"<staff password>"}' \
  | grep -i "set-cookie"
# expect: SameSite=None; Secure  —  Strict here means WEB_ORIGINS did not apply.
```

Then sign in from the live Pages page in Chrome or Firefox and add something to
the basket. The basket surviving a reload is the real test.

## What will bite you

- **The free API sleeps.** Fifteen minutes without traffic spins it down and the
  next request waits about a minute while it wakes. Tell your audience before
  they tap "sign in". Do not add an uptime pinger to avoid this: a free
  workspace gets 750 instance hours a month and one always-on service consumes
  nearly all of them, which suspends every free service in the workspace until
  the next month.
- **The free database expires 30 days after it is created.** It becomes
  unreachable, and Render deletes it 14 days later unless you upgrade it. For a
  demo after that window you either upgrade the plan or create a new database
  and repeat step 2.
- **The API's filesystem is wiped** on every redeploy, restart and spin-down.
  Admin-uploaded product images live in `UPLOAD_DIR` and are lost. Nothing breaks
  today because the shop renders bundled images from `src/assets` and never asks
  the API for a file. Attach a persistent disk (paid) before uploads matter.
- **Safari and Chrome-on-iOS will not sign in.** The session cookie belongs to
  `*.onrender.com` while the page belongs to `github.io`, so it is third-party
  and Apple's Intelligent Tracking Prevention drops it. This is not fixable with
  cookie flags. The fix is one registrable domain shared by both halves:

  | Shop | API |
  | --- | --- |
  | `https://shop.example.com/` | `https://api.example.com/` |

  Point Pages' custom domain at the Pages site (`CNAME` plus a domain in GitHub
  Settings → Pages), add the domain to the Render service, then set
  `WEB_ORIGINS=https://shop.example.com` and rebuild the shop with
  `API_BASE_URL=https://api.example.com`.
- **The Docker stack is the same-origin path.** `docker compose up` puts nginx in
  front of both, so leave `WEB_ORIGINS` unset there. Its entrypoint runs
  `drizzle-kit migrate` and there are no committed migrations in `api/drizzle`,
  so the schema arrives by `npm run db:push`, as in step 2 — a fresh stack boots
  against an empty database until that has been run.
